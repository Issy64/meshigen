# handson-start

meshigen プロジェクトで GitHub Issue に着手するときの **準備フェーズ専用** スキル。
コード実装そのものはユーザーの手で行う（ハンズオン学習が目的）ため、このスキルは
「準備 → タスク分割 → ブランチ作成」までで止まる。

## 起動条件

ユーザーが次のように言ったとき：

- 「ISSUE#NN に着手する」「#NN のハンズオン準備をして」「Issue NN を始める」
- 引数として Issue 番号が与えられている

引数が無い場合は Issue 番号を聞き返すこと。

## 進め方の原則

このプロジェクトはポートフォリオ用で、ユーザー（Issy64）は基礎を学んだ上で
**自分でコードを書きたい** と考えている。エージェントが先回りして全部書かない。

- 設計判断・仕様の読み解き・現状把握はエージェントが主導する
- 実装コードは **ユーザーが書く**（エージェントはステップごとに手順を示す）
- 1機能1コミットを意識し、コミットメッセージは段階的設計が読み取れるようにする

## 実行手順

### STEP A: Issue内容と現状の把握（並列実行）

以下を **並列の Bash 呼び出し** で取得する：

1. `gh issue view <NN>` — Issueの本文・タイトル・状態
2. `gh issue view <親番号>` — 本文に `Parent issue` がある場合に取得
3. `git status` と `git branch --show-current` — 作業ツリーが clean か、現在ブランチ
4. Issue本文の `## Target files`（新規 or 修正）に挙がっているファイルの存在確認
   - 既存ファイル: `Read` でざっと内容を見る
   - 新規ファイル: 親ディレクトリの存在確認
5. 関連する型・パッケージが既に存在するか `find` / `Read` で確認
   （例: Issueが `GourmetEntity` を参照しているなら、本当に存在し期待のフィールドを持つかを見る）

### STEP B: ユーザー向けサマリの提示

次の3ブロックで要約する：

1. **ISSUE概要** — 1〜3行で「何を作る／作らない」を書く。
   特に `Non-scope` を明示すると次サブIssueの境界が見えやすい。
2. **現状確認** — 箇条書きで
   - 現在ブランチ／作業ツリーの状態
   - 関連ファイルの有無
   - 既存依存・既存型の状態
   - Issueの仕様との差分（足りないもの）
3. **ハンズオン作業の見取り図** — 番号付きで5〜10ステップに分解。
   各ステップは「何を／どのファイルに」レベルで十分。コード本体は書かない。

### STEP C: 進め方の合意（AskUserQuestion）

最低1つ、必要なら2〜3つ質問する：

- 必須: **ハンズオンの進め方**
  - 「ステップごとに手順を示し、ユーザーがコードを書く」（推奨：学習効率重視）
  - 「エージェントがたたき台を書き、ユーザーがレビュー・修正」（スピード重視）
  - 「面倒なボイラープレート（Gradle 等）はエージェント、設計反映型はユーザー」
- Issueに固有の判断分岐があれば追加で聞く
  （例: 外部設定ファイルを今扱うか後回しか、フォールバック方針、テスト方針 など）

### STEP D: タスク分割（TaskCreate）

STEP B-3 の見取り図に対応する TaskCreate を 1ステップ1タスクで作る。
最後のタスクは必ず **「コミット & PR 作成」** を含める。

### STEP E: ブランチ作成

1. `git pull origin main` で最新化（既に最新なら no-op）
2. `git switch -c Issy64/issue-<NN>-<短いkebab-slug>` で作業ブランチ作成
   - slug は Issueタイトルから英語の要点を抜く（例: `#81` の "AI候補取得の境界を定義" → `ai-matcher-boundary`）
   - 過去ブランチ命名規則: `Issy64/issue-NN-<topic>` を踏襲
3. `TaskUpdate` で「ブランチ作成」タスクを `completed` に
4. 「次の STEP は ◯◯ です。合図をください」と短く締める

## やってはいけないこと

- ❌ コード本体（Kotlin/Gradle設定など）を勝手に書く
  → このスキルはあくまで「準備」まで
- ❌ STEP C の合意なしに次のSTEPへ進む
- ❌ Issue本文をそのままコピペで貼り付ける
  → 必ず要約する（特に Non-scope を強調）
- ❌ ブランチ名で日本語や長すぎる slug を使う
- ❌ TaskCreate を 1つだけにまとめる
  → ハンズオン中の進捗が見えなくなるので、必ず複数ステップに分割

## 終了状態

- 作業ブランチが切られ、`git branch --show-current` で確認できる
- タスクリストに 5〜10 件の pending タスクが並んでいる
- ユーザーが「STEP 2」と言えば次の手順を出せる状態
